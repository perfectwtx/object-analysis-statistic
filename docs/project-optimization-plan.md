## 1. 当前判断

项目已经具备数据分析与质量管理平台的基本结构，覆盖工作台、质量看板、趋势、字段质量、问题中心、基线、告警、关系、血缘与影响分析。

技术栈为 React 18、Vite 5、React Router 6、Zustand、Tailwind CSS、Recharts。前端提交文件与规则，调用 .NET 后端进行分析，再通过适配层展示结果。较大文件默认走异步任务，通过 SSE 获取进度，连接失败后回退轮询。

目前应先保证结果真实、规则正确和任务状态可靠，再推进性能与维护性优化。暂不建议进行大规模重写或整体更换技术栈。

## 3. P1：正确性与业务可靠性

### 01. 分离演示数据与真实数据

**现状与影响**

- `src/lib/load-platform.js` 在真实作业列表为空时回退到 `SEED_JOBS`。
- 缺少维度分数时补入 `SEED_DIMS`，缺少趋势时调用 `buildTrend()` 生成演示趋势。
- 基线、告警接口不可用时也会补入演示数据；返回的 `fields` 固定为 `SEED_FIELDS`。
- 同一份返回结果可能同时标记 `source: 'api'`，页面因此可能把演示指标展示为真实结果。

**建议方案**

- 将演示模式作为显式入口或配置，不以接口异常、空数组作为启用演示数据的条件。
- API 成功但数据为空时展示空态；接口未实现时展示能力未启用；请求失败时展示错误和重试入口。
- 对作业、趋势、维度、基线、告警分别记录来源和加载状态。
- 不使用演示分数补齐真实分数；缺失值显示“暂无数据”，避免参与均值计算。

**验收标准**

- 新环境没有任何作业时，作业列表为空，不出现样例作业。
- 部分接口未实现时，其他已实现模块仍展示真实数据。
- 页面明确标识演示模式，API 模式不会混入示例指标。

### 02. 修复清空规则后仍使用旧规则

**现状与影响**

`src/workbench/WorkbenchShell.jsx` 的 `clearRules()` 先调用 `setRules(null)`，随后调用 `runAnalysis(source, null)`。但 `runAnalysis()` 的第二个参数没有用于选择规则，第三个参数才是规则覆盖值；未提供第三个参数时仍读取当前闭包中的旧 `rules`。

因此，已应用规则后点击清空，界面虽然变为空规则，但紧接着发出的分析仍可能携带旧规则。

**建议方案**

- 清空后重跑时显式传入空规则覆盖值，例如 `runAnalysis(source, null, null)`。
- 后续把执行入口改为明确的参数对象，删除未使用的 `_rulesJsonText` 参数，降低参数错位风险。
- 明确区分规则草稿与已应用规则，确保按钮行为和实际提交一致。

**验收标准**

- 应用一条会影响结果的规则，再点击清空，下一次请求不携带旧 `rulesJson`。
- 字段过滤、预检和规则警告同步采用清空后的规则状态。

### 03. 完善任务取消、卸载清理与结果隔离

**现状与影响**

`src/hooks/useAsyncAnalyze.js` 存在以下缺口：

- 定义了 SSE、轮询清理函数，但没有注册组件卸载清理。
- 异步提交没有统一接入内部 AbortController。
- 提交尚未返回 jobId 时取消，收到响应后直接返回，没有继续取消新创建的后端任务。
- 新任务启动和 reset 没有完整中止旧请求，也缺少任务版本标识，旧响应可能继续更新状态。
- 在检查 `EventSource` 是否存在前就创建 SSE 连接，无 EventSource 环境下无法进入预期的轮询回退。
- 轮询失败只记录日志，没有重试上限或退避策略。

**建议方案**

- 组件卸载时关闭 SSE、停止轮询并中止前端请求；是否取消后端任务按产品需求确定，避免离开页面就误取消长任务。
- 每次执行分配递增标识，只有当前执行的响应可以更新状态。
- 提交阶段取消后，若随后取得 jobId，应补发后端取消请求；后端是否需要额外支持幂等提交需联调确定。
- 先判断 EventSource 可用性，再选择 SSE 或轮询。
- 对明确不存在的作业停止轮询，对临时网络故障使用有上限的退避重试。

**验收标准**

- 离开分析页后不会继续产生该页面的轮询请求或保留 SSE 连接。
- 连续提交、取消后重试时，旧任务结果不会覆盖当前任务。
- 提交阶段取消能正确处理延迟返回的 jobId。
- 不支持 SSE、SSE 断连、作业过期时均有明确终态或恢复行为。

### 04. 告警开关写入后端

**现状与影响**

`src/pages/AlertRulesPage.jsx` 使用 store 中的 `toggleAlert()`。该操作只修改本地数组，没有调用已经封装的 `updateAlertRule()`，因此界面切换不代表服务端规则已生效，刷新后也可能恢复。

**建议方案**

- 真实数据模式下通过后端接口保存启用状态，并展示提交中状态。
- 保存失败时保留原状态或回滚，并提供明确错误反馈。
- 演示模式下明确说明切换仅用于演示。
- 联调确认后端更新接口要求完整规则还是部分字段，避免遗漏阈值、Webhook 等配置。

**验收标准**

- 开关切换成功后刷新页面，状态保持一致。
- 后端拒绝或网络失败时，界面不会保持虚假的保存成功状态。

## 4. P2：稳定性、性能与质量保障

### 05. 平台接口局部失败隔离

**现状**：总览使用 `Promise.all` 聚合多个请求，任一请求抛错会进入整体演示回退；健康检查先行执行，基线和告警后续又串行加载。

**建议**：按模块处理成功与失败，可使用 `Promise.allSettled`；无依赖的请求并行执行；避免趋势与快照重复请求相同能力；复用请求缓存和刷新逻辑。

**验收**：趋势接口返回 500 时，作业和问题仍可显示；失败模块可单独重试；健康检查慢不会阻止其他模块开始加载。

涉及：`src/lib/load-platform.js`、`src/lib/store.js`。

### 06. 统一接口契约与能力探测

**现状**：`src/api/platform.js` 对多个接口依次尝试别名路径，读写路径的兼容方式并不完全一致；虽有 `getCapabilities()` 封装，但当前菜单和平台加载没有形成统一的能力控制。

**建议**：与后端确认标准路径、状态枚举、分页结构、空态语义和字段命名；通过 capabilities 或部署配置决定支持的模块；仅在确需兼容旧版本时保留路径回退，并缓存探测结果。可先采用 JSDoc 与响应校验完善类型约束，再评估是否逐步引入 TypeScript。

**验收**：支持与不支持的能力均有稳定显示；缺失接口不会每次刷新都重复探测全部别名；列表可读时，对应写入路径也与当前后端版本匹配。

### 07. 防止作业切换后旧请求覆盖新结果

**现状**：`JobDependentPage.jsx`、`FieldQuality.jsx` 等页面异步加载缺少取消或响应版本检查。快速从作业 A 切换到 B，如果 A 最后返回，可能显示 A 的数据而选择器仍指向 B。

**建议**：在 effect 清理时取消旧请求，或通过请求序号丢弃过期响应；手动刷新与自动加载共用同一套请求管理；覆盖每个异步入口的错误处理，例如字段质量页首次加载作业列表目前只有 `finally`。

**验收**：人为延迟 A 的响应并切换到 B，最终仍只显示 B 的数据；请求失败被页面捕获，不出现未处理的 Promise 拒绝。

### 08. 路由懒加载与包体积优化

**验证结果**：通过本地 Vite 入口构建成功，主 JS 约 805 KB，gzip 约 238 KB；Excel 导出独立 chunk 约 429 KB，gzip 约 143 KB。Vite 提示主 chunk 超过 500 KB。数值来自本次环境构建，不等同于实际网络加载时间。

**建议**：优先对低频分析页面和工作台使用 `React.lazy`、`Suspense`；保留 Excel 按需导入；再根据构建结果评估图表依赖分包，避免只拆包却没有减少首屏加载量。

**验收**：打开首页不会立即下载所有业务页面代码；切换页面具有加载反馈；优化前后比较首页实际加载字节数和请求瀑布。

涉及：`src/App.jsx`、`vite.config.js`。

### 09. 为关键业务增加自动化检查

**现状**：`package.json` 只有 dev、build、preview 脚本，未发现测试文件、独立 lint 脚本或 CI 配置。

**建议覆盖**：

- 规则应用与清空的请求参数正确性。
- 后端返回空列表时不混入演示数据。
- 任务取消、SSE 回退和过期响应隔离。
- JSONC 清洗、响应适配与核心导出边界。
- 在 CI 中执行构建、静态检查和上述关键测试。

**验收**：能够自动发现前述规则清空和数据回退问题；检查覆盖业务行为，避免只断言组件内部实现。

### 10. 完善导出内容与失败反馈

**现状**：`src/exporters.js` 的 CSV 转义处理了逗号、双引号和换行，但未单独处理回车；以公式前缀开头的字段名、默认值等内容可能被电子表格软件解释为公式。Markdown 表格没有转义管道符和换行。工作台异步导出也缺少统一错误反馈。

**建议**：增加适用于导出的单元格规范化；明确 CSV 公式防护策略及对原始文本的影响；转义 Markdown 表格内容；捕获 Excel 动态加载、内容生成和保存失败；大结果是否需要服务端导出，根据实际数据规模决定。

**验收**：包含逗号、引号、回车换行、管道符和公式前缀的样例可正确导出；失败时页面给出可操作的提示。公式防护应在目标表格软件中实测。

## 5. P3：维护性与体验

### 11. 统一主题状态与样式职责

**现状**：`src/theme.js` 与 `src/lib/store.js` 都管理主题，`ThemeSwitch` 同时调用两者。主题模式、解析后的主题和持久化存在重复维护。项目还同时加载多份全局样式。

**建议**：统一主题状态入口，明确 mode 与 resolvedTheme；保留首屏主题预置，与运行时复用一致的规则。梳理样式职责和覆盖顺序，逐步清理重复样式。删除疑似旧文件前先确认引用关系。

**验收**：系统主题变化、手动切换、跨标签页同步和护眼模式表现一致；图表与页面主题一致；样式调整不依赖不断追加覆盖规则。

### 12. 拆分工作台业务编排

**现状**：`WorkbenchShell.jsx` 同时处理数据源、规则草稿、规则校验、预检、分析、导出、侧栏拖拽和本地配置，参数传递较多。

**建议**：优先按规则管理、分析编排、报告导出拆出 hooks 或独立函数；将请求参数构造集中为纯函数；预检与分析复用同一份有效选项，避免两阶段字段支持不一致。保留现有布局，逐项迁移。

**验收**：一次规则或请求选项调整只需修改一个明确入口；预检和正式分析参数一致；原有主流程行为保持稳定。

### 13. 完善多语言与交互一致性

**现状**：平台存在语言切换，但工作台标签、错误和配置文本仍有硬编码中文；不同页面分别实现加载、错误、空态和接口不可用提示。

**建议**：逐步将面向用户的文本接入统一字典；复用现有 LoadingBlock、ErrorBanner、EmptyState 等组件；对模态框、键盘操作、焦点恢复、侧栏拖拽替代操作和窄屏布局进行实际检查。可访问性和移动端问题目前属于待验证事项。

**验收**：切换语言后主要业务流程文本一致；无数据、无能力、失败、加载四种状态可区分；主要流程可用键盘完成。

### 14. 更新文档、部署说明与本地运行指引

**现状**：README 的 App/API 结构说明仍偏向旧版；宣称支持 PDF，但当前工作台导出菜单未看到 PDF 入口。API 缺口文档中的能力状态也需与实际部署重新核对。

本次环境执行 `npm run build` 时，系统 npm 启动脚本指向缺失的 npm-cli.js；直接运行 `node node_modules/vite/bin/vite.js build` 可完成构建。这是本地工具链问题，尚不能认定为仓库代码缺陷。

**建议**：更新架构图、目录说明、功能支持表、API 配置和后端联调步骤；说明 BrowserRouter 在生产托管时需要页面刷新回退到 index.html；明确 Vite 开发代理不会随静态构建产物一起部署，生产需反向代理或配置可访问的 API 地址。核查 npm 安装路径；用实际验证过的说明替换旧的缓存与删除规避指引。

**验收**：新环境可按文档完成安装、构建与后端连接；生产直接刷新子路由正常；文档列出的功能与界面入口一致。

## 7. 实施前需要确认的后端事项

- 异步任务可能出现哪些状态，是否包含排队状态，取消接口是否幂等。
- 同步分析是否返回持久化 jobId，以及分析完成后历史与质量快照何时可查询。
- capabilities 是否已部署，标准路径、列表包装与分页契约是什么。
- 告警、基线的写入路径和请求体是否与当前前端封装一致。
